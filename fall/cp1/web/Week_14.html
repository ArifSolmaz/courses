01 / The situation

What evidence supports the report—not just the fact that it runs?

Use the existing Week 14 sensor-log project as a small engineering handover. The supplied 20-record fixture contains temperature, humidity and pressure data. Deliver the cleaned CSV and report, then demonstrate a fault case that your pipeline handles honestly.

Your handover

sensor_data_clean.csv, sensor_report.txt, a rejection record, and a brief handover explaining one independent check and one deliberately injected fault.

Start on paper. Work alone or in a pair: one person predicts, the other challenges the assumptions; swap roles halfway through. All essential data is provided. No hardware or AI account is required.

02 / Build a model

Understand what the code represents.

Connect the contracts

The input schema is timestamp,sensor,value. Read → validate → group → summarize → save. Each stage should have a clear input and output so a discrepancy can be localized. Validate structure, known sensor, timestamp, numeric conversion, finiteness and the sensor-specific range.

Use independent reference checks

The supplied fixture has 15 retained and 5 rejected records. Temperature has 6 readings with mean 23.02 °C; humidity has 5 with mean 45.38%; pressure has 4 with mean 1012.86 hPa. These are reference results for the supplied file, not targets to hard-code.

A clean report has limits

A 75% retained-row rate describes your validation policy on this file. It is not a sensor-accuracy score or proof that the machine is healthy. Valid-range data can still contain bias, stale readings or a swapped sensor label.

Explain the empty case

If a sensor has no valid values, display count 0 and N/A for statistics. Do not call min() on an empty group or substitute zero. Keep units separate; comparing temperature and pressure means numerically has no shared physical meaning.

Inspect the small Python model

Read and predict first. Run this self-contained example in a new notebook cell; use the result as evidence to discuss.

temperature_c = [22.5, 23.1, 22.8, 23.5, 24.0, 22.2]
retained = 15
rejected = 5
assert retained + rejected == 20
print(f'Temperature mean: {sum(temperature_c) / len(temperature_c):.2f} C')
print(f'Retained-row rate: {100 * retained / (retained + rejected):.1f}%')

Reference output

Temperature mean: 23.02 C
Retained-row rate: 75.0%

This short cell is an independent arithmetic check, not the pipeline implementation. Build and test the complete program through notebook milestones EX01–EX10. Teaching acceptance ranges are temperature −50–60 °C, humidity 0–100%, and pressure 800–1200 hPa, all inclusive.

03 / Predict & inspect

Try to break your first explanation.

These are prepared teaching cases, not live sensor readings or an automatic grade. Write a prediction before opening a case, then reveal the reasoning one step at a time. Explain any disagreement.

01Supplied fixture

20 records; 15 retained; 5 rejected; temperature sum 138.1 over 6 readings

Predict: Predict the retained-row rate and displayed temperature mean.

  1. 15 / 20 × 100 = 75%
  2. 138.1 / 6 = 23.0166…
  3. Display temperature mean as 23.02 °C

75.0% retained; temperature mean 23.02 °C

These checks test counts and arithmetic. They do not replace checking each rejected row and the saved output.

02Empty sensor group

After validation, pressure has no retained values

Predict: What should count, min, max and mean show?

  1. Count = 0
  2. No values exist for min or max
  3. Mean has no valid denominator

Count 0; min/max/mean N/A

An explicit absence is a legitimate result. A numeric zero would invent a pressure measurement.

03Plausible sensor bias

Add 5 °C to every valid temperature in the supplied fixture

Predict: Will range validation necessarily detect this bias?

  1. Original valid temperatures span 22.2–24.0 °C
  2. Shifted values span 27.2–29.0 °C, still inside −50–60
  3. Mean shifts from 23.0166… to 28.0166… °C

Range checks pass; displayed mean becomes 28.02 °C

A plausible value is not necessarily an accurate measurement. Investigating bias needs independent evidence such as a reference sensor.

04 / Investigate

One question. Several kinds of evidence.

  1. State the input schema, sensor ranges, timestamp rule and output filenames. Use the supplied dataset setup in EX01.
  2. Complete EX02–EX10 as connected milestones. At each boundary, inspect a small intermediate result before continuing.
  3. Verify 20 = 15 + 5 and the per-sensor counts 6, 5 and 4. Check the temperature sum by hand, then reopen sensor_data_clean.csv and sensor_report.txt.
  4. In a copy of the input, inject one fault: an unknown sensor, nonfinite value, malformed timestamp or an empty sensor group. Predict the outcome before running.
  5. Re-run the full program in a fresh runtime, then give a three-minute handover: claim, evidence, failure handled and remaining limitation.
Keep the evidence

sensor_data_clean.csv, sensor_report.txt, a rejection record, and a brief handover explaining one independent check and one deliberately injected fault.
