In what order do we start the robot?

15 min · Engineering question

The robot must boot before scanning or enabling its drive. Scan precedes map loading. Map and drive must both be ready before run. Draw each arrow from prerequisite to dependent.

Start with the rule, then draw the arrow

A robot startup script cannot load a map before its scan is ready, and it cannot run before both map and drive are ready. We want a list containing every task exactly once, with each prerequisite earlier than its dependent. This is a topological order. A directed graph that has no directed cycle is called a DAG; exactly such graphs admit a topological order.

TaskMeaningDirect prerequisites
bootInitialize the robot—
scanAcquire a scanboot
drivePrepare the driveboot
mapLoad/build the mapscan
runBegin operationmap, drive

Use prerequisite → dependent: “scan must finish before map” becomes scan→map. The adjacency list graph['scan'] contains 'map', not 'boot'. Incoming arrows express what a task needs; outgoing arrows show which tasks depend on it. We assume these are strict finish-before-start requirements on a fixed graph.

Remember: Week 8 · Connections have a new meaning

BFS on the 2×2 map S. / .G returned a two-move route. Here boot→scan is not a move the robot drives: it is a requirement on task order. A route visits selected cells; a complete startup order must include every listed task, including disconnected ones.

Remember: Week 9 · No route-cost minimization this week

Dijkstra chose eight moves costing 8 over four moves costing 28. Dependency ordering has no such sum to minimize: boot,drive,scan,map,run and boot,scan,map,drive,run both satisfy the original arrows.

Remember: Week 10 · A target heuristic does not enforce prerequisites

A* used f=g+h; for g=1 and h=3 the priority was 4. A small estimate toward run would not authorize run to start before drive finishes. We need an ordering rule that respects every dependency, not a distance estimate to a goal.

Turn prerequisites into a valid startup order

You will be able to

  • Draw arrows from prerequisite to dependent.
  • Trace unseen, active and finished states.
  • Reverse finish order on an acyclic graph.
  • Find a cycle witness.

Three marks describe the analysis

StateCodeMeaning in DFSWhat an edge to it means
Unseen0Not entered yetExplore it recursively
Active1On the current unfinished call chainA directed cycle is present
Finished2All outgoing edges have been examinedAlready analyzed; do not recurse again

DFS does not execute robot tasks. “Enter map” means analyze the map vertex; “finish run” means finish examining its outgoing edges. It does not mean the robot ran before boot. First compute and validate the order; only then may a separate controller execute tasks, checking that prerequisites actually succeed.

Depth-first search follows a branch before returning. Mark a task active when entering it and finished after all outgoing edges have been examined. An edge to an active task returns to the current chain and closes a cycle. An edge to a finished task does not by itself prove a cycle.

When the graph is acyclic, reverse the order in which tasks finish. This places each prerequisite before its dependents. Start another DFS from any still-unseen task so the result includes disconnected tasks too.

A valid order can be checked by writing the position of each task and testing every arrow. Even if a different tie rule changes the order, every dependency must point forward.

Trace the full startup graph

Start at boot; examine scan before drive. The active chain below is the recursion stack, with the newest task at the right. Finished tasks leave that chain and join a separate finish list.

Finish runboot, scan, maprun

Reverse the finish list: boot, drive, scan, map, run. The discovery order was boot, scan, map, run, drive, which is invalid as an execution order because run comes before its prerequisite drive. Reversing discovery also fails: it would put boot last.

Why reverse finishing works

Consider any edge u→v in an acyclic graph. If v is unseen, DFS finishes exploring v before it can finish u. If v is already finished, v is again earlier in the finish list. v cannot be active without forming a cycle. Therefore v always finishes before u, and reversing the list places u before v for every edge.

Remember: Week 5 · A visited flag loses important information

A dictionary can store state['run']=2 while state['boot']=1. Both tasks have been visited, but an edge to boot closes the current chain, whereas drive→run can safely reach a finished task. Store three states, not just membership in a visited set.

Turn a back edge into an exact cycle

Add run→boot. While analyzing run, the active chain is boot,scan,map,run. The target boot is active, so append it to close the witness: boot→scan→map→run→boot. Every arrow in that sequence exists. It would require boot to finish before itself through strict prerequisites, which is impossible. The witness proves one cycle exists; it does not list all cycles or tell us which requirement should be removed.

Remember: Week 1 · One witness can justify an early exit

Scanning [2,9,12] for any value above 8 may stop at 9. Similarly, finding one directed cycle is enough to answer “no complete topological order exists.” Finding no cycle in just the boot component is not enough to accept the whole graph: other components must also be checked.

Separate a valid order from the order of a DFS walk

Tasks A and B are independent prerequisites of D. A is also a prerequisite of C, and C is a prerequisite of D. Start DFS at A, visiting C before D. Then visit B.

Show the worked steps
  1. A opens C, then C opens D. D finishes first, then C. A’s other edge to D finds it finished.
  2. A finishes third. B starts after A finishes and sees D already finished. Finish order is D, C, A, B, so one valid order is B, A, C, D.
  3. Add D→A. DFS from A then reaches the active A again through C and D. The cycle is A→C→D→A.

Compare the two traces. Record one boundary case and a clue that would expose a wrong result. Then take a 10-minute break.

Run a planner that explains a cycle

This standalone example uses readable task names. The dictionary lists dependents, and every task—including a leaf with no dependents—must have a key. Dictionary and neighbor-list order make the example deterministic; another order can produce a different valid answer. The function returns either (order, []) or (None, cycle).

def plan_startup(graph):
    # Keys are task names; each list contains their dependents.
    if any(v not in graph for edges in graph.values() for v in edges):
        raise ValueError("Every dependent must be a graph key")
    state = {task: 0 for task in graph}
    active = []
    active_position = {}
    finish = []

    def visit(task):
        state[task] = 1
        active_position[task] = len(active)
        active.append(task)
        for dependent in graph[task]:
            if state[dependent] == 1:
                i = active_position[dependent]
                return active[i:] + [dependent]
            if state[dependent] == 0:
                cycle = visit(dependent)
                if cycle:
                    return cycle
        active.pop()
        del active_position[task]
        state[task] = 2
        finish.append(task)
        return []

    for task in graph:
        if state[task] == 0:
            cycle = visit(task)
            if cycle:
                return None, cycle
    return finish[::-1], []

graph = {
    "boot": ["scan", "drive"],
    "scan": ["map"],
    "drive": ["run"],
    "map": ["run"],
    "run": [],
}
order, cycle = plan_startup(graph)
print("Order:", " -> ".join(order))
assert len(order) == len(graph) and set(order) == set(graph)
position = {task: i for i, task in enumerate(order)}
assert all(position[u] < position[v] for u in graph for v in graph[u])

graph["run"].append("boot")
order, cycle = plan_startup(graph)
print("Order after change:", order)
print("Cycle:", " -> ".join(cycle))
assert order is None
assert cycle[0] == cycle[-1]
assert all(v in graph[u] for u, v in zip(cycle, cycle[1:]))

Try adding graph['log']=[] before the first call: the isolated task must appear once, and this traversal places it first in the final order. For a second experiment, replace the line graph["run"].append("boot") with graph["run"]=["run"]: the witness becomes run→run, a self-loop. Restore the original example between experiments. This recursive teaching version is for small graphs; long dependency chains require an explicit stack or another nonrecursive method.

Validate any proposed order without rerunning DFS

For boot,drive,scan,map,run, positions are boot=0, drive=1, scan=2, map=3, run=4. Check every edge: 0<2, 0<1, 2<3, 3<4, 1<4. Also check length and membership so missing or duplicated tasks cannot pass accidentally. On the A,B,C,D,I graph, I,B,A,C,D is valid; I can move anywhere without violating an edge.

Remember: Week 3 · This is not sorting by task ID

Binary search needs a sorted key sequence such as [10,20,30,40]. Topological order instead respects edges: if task 3 must precede task 1, ascending IDs [0,1,2,3] are not a valid general solution. A position dictionary makes dependency checks direct.

Common mistakes

  • Reversing the discovery list instead of the finish list.
  • Treating all visited neighbors as evidence of a cycle.
  • Forgetting isolated tasks.

A second viewpoint: which tasks are ready?

Kahn’s algorithm starts with each task’s indegree: its number of incoming prerequisites. Repeatedly remove a zero-indegree task, append it to the order, and decrement its dependents’ counts. Add a dependent to the ready queue only when its count reaches zero. If fewer than V tasks are removed and the queue is empty, a directed cycle remains. This is an alternative planning algorithm; it still does not execute the tasks.

RemoveCount changesReady FIFO after update
Initial stateboot:0, scan:1, drive:1, map:1, run:2boot
bootscan:1→0, drive:1→0scan, drive
scanmap:1→0drive, map
driverun:2→1map
maprun:1→0run
run—[]

The result boot,scan,drive,map,run differs from the DFS result but passes the same edge test. In particular, removing drive does not make run ready yet: map remains a prerequisite. With a cycle, the unremoved set may contain both cycle members and tasks blocked downstream; it is not itself an exact cycle witness.

Remember: Week 4 · FIFO and LIFO do different work

A FIFO containing scan,drive returns scan and leaves drive. Kahn uses a FIFO of ready tasks in this trace. Recursive DFS instead uses a LIFO call stack: entering boot,scan,map,run returns from run first. Replacing the stack with a queue without changing the algorithm is not DFS.

Remember: Week 7 · Priority may break ties only among ready tasks

A min-heap with deadlines 3 and 7 returns 3 first. You may use a heap to choose among zero-indegree tasks, for example preferring diagnostics to power. Even the highest-priority enable task cannot be selected while its prerequisites remain. A priority policy chooses a valid order; it does not guarantee the fastest complete schedule.

Count edges and stack depth separately

Remember: Week 2 · A nested loop is not automatically quadratic

Comparing every pair of n items takes about n² operations. DFS’s inner loop scans graph[u], so across all vertices it scans E stored edges, not V edges for every vertex. With adjacency lists, DFS takes O(V+E) time and O(V) extra space for states, finish order and the call stack. Stored graph data takes O(V+E) space separately.

GraphVEMaximum active tasks
20-task chain201920

The chain and star have the same V and E but very different call depths. Increasing n far beyond the classroom examples can exceed Python’s recursion limit. RecursionError means the implementation ran out of call-stack capacity; it is not evidence of a graph cycle. For large graphs use iterative DFS frames that preserve the next-neighbor position, or Kahn’s algorithm. Simply pushing task IDs and reversing their discovery order does not reproduce DFS finishing order.

Remember: Week 6 · Timing summaries are not deadline guarantees

The median of sorted samples [2,2,3,7,100] is 3. Our lab reports a median and largest of five batch averages, not the slowest possible individual call. A cycle may stop traversal early, depending on where it is found; a cycle at the end of a long chain does not save visiting that chain.

Measure it

Predict the work for dependency chains of 20 and 200 steps. Time the DFS with both inputs and add a final edge to the first task. Check that the cycle is reported.

Select Run or copy the code into Python 3. The two times are the median and largest of five batch averages, in milliseconds per call. The largest batch average does not bound an individual call.

The compact lab uses integer task IDs 0…n−1: graph[u] lists the dependents of u. Every task gets a list, even if empty. The new validation rejects negative, out-of-range or noninteger dependent IDs before DFS. The input is an adjacency list with reusable neighbor lists, and it must not change during the search. Unlike the named example, this compact function returns only an order or None, not a cycle witness.

from statistics import median
from timeit import repeat


def measure(label, job, repeats=200):
    samples = repeat(job, repeat=5, number=repeats)
    typical = median(samples) * 1000 / repeats
    longest = max(samples) * 1000 / repeats
    print(f"{label:18}  {typical:.6f} ms  {longest:.6f} ms")

def topological(graph):
    n = len(graph)
    if any(type(v) is not int or not 0 <= v < n for edges in graph for v in edges):
        raise ValueError("Dependents must be integer task IDs from 0 to n-1")
    state = [0] * len(graph)
    finish = []

    def visit(task):
        if state[task] == 1:
            return False
        if state[task] == 2:
            return True
        state[task] = 1
        for dependent in graph[task]:
            if not visit(dependent):
                return False
        state[task] = 2
        finish.append(task)
        return True

    for task in range(len(graph)):
        if not visit(task):
            return None
    return finish[::-1]


for n in (20, 200):
    graph = [[i + 1] for i in range(n - 1)] + [[]]
    assert topological(graph) == list(range(n))
    measure(f"{n}: chain", lambda: topological(graph))
    graph[-1].append(0)
    assert topological(graph) is None
    measure(f"{n}: cycle", lambda: topological(graph))

Design a safe startup after a dependency is added

Boot precedes power and diagnostics. Power precedes actuator check, diagnostics precedes sensor check, and both checks precede enable. A configuration error adds enable→power.

Start individually for 10 minutes. Work with a partner for 20. Spend the last 15 comparing with another pair and revising your recommendation.

  1. Draw the six tasks and directed dependencies. Give two valid orders before the extra edge, and check them by marking each edge forward.
  2. Identify a cycle after the extra edge. Explain why changing the tie rule cannot fix it.
  3. Recommend what the controller should report when a cycle is found. Explain whether it is safe to enable on a partial order.
Compare a model answer

One valid order is boot, power, diagnostics, actuator check, sensor check, enable. Another is boot, diagnostics, sensor check, power, actuator check, enable. The error creates power→actuator check→enable→power. Report the loop and keep enable blocked until the configuration is corrected.

A valid list is not yet a complete runtime scheduler

Before executing startup, validate the complete graph and order. Report a concrete loop such as power→actuator check→enable→power and leave enable blocked until an authorized configuration correction resolves it. Do not silently delete an edge or use a partial finish list as a complete plan. Whether independent diagnostics may run after rejection requires a separate, explicit operating policy.

Topological order also does not model duration, resource conflicts or task failures. Return to the original five-task graph and suppose durations are boot=2, scan=3, drive=1, map=2, run=1 time units. Sequential execution totals 9. With unlimited resources and successful tasks, boot runs 0–2, scan 2–5 and drive 2–3 in parallel, map 5–7, and run 7–8. Completion takes 8 units because the boot→scan→map→run chain controls it. This timing calculation is extra information, not part of the DFS result.

Try the same model outside robotics

A data pipeline may require download→clean, clean→train, train→evaluate, and clean→report. One valid order is download,clean,report,train,evaluate. Adding evaluate→clean creates clean→train→evaluate→clean. A build system uses the same rule: compile a library before linking its dependent application. Only encode real prerequisites; unrelated tasks need no invented ordering edge.
