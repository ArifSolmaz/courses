The sorting contract

Input: an array of records containing a device ID and location label. IDs in this directory are distinct. Output: all the same records, with IDs in increasing order. No record is lost or added; each label moves with its ID.

n is the number of records: 8 here. One ID comparison is a single abstract operation giving the less-than/equal-to/greater-than relationship between two numbers. The magnitude of a device ID is not n.

Predict the output first

Is moving only the smallest ID, 4, to the front enough? Can 31’s “gate” label move to a different record?

Compare my contract

No. All records must be sorted: [4, 7, 11, 18, 20, 24, 26, 31]. 31 still carries “gate”. Selecting the minimum produces just one result; sorting produces the whole order.

02 · Solve one merge first

If both pieces are already sorted,
look only at their heads.

Suppose the left piece [7:greenhouse, 18:pump] and right piece [4:roof, 24:warehouse] are already sorted. Each head record is the smallest remaining record in its piece. Take the smaller head for the next output position.

  1. Compare 7 with 4 → output 4:roof. The right head is now 24.
  2. Compare 7 with 24 → output 7:greenhouse.
  3. Compare 18 with 24 → output 18:pump. The left piece is exhausted.
  4. Only 24:warehouse remains on the right → output it without a comparison.

Result [4, 7, 18, 24]. 3 ID comparisons, 4 output placements. We added one whole record at each output step; once a piece was exhausted, we kept taking the remainder without new comparisons.

Why is the decision safe?

When both pieces are sorted, their heads are the smallest remaining candidates. Taking the smaller head takes the smallest of all remaining records. We can continue while preserving output order. This reasoning does not apply if the inputs are unsorted.

If IDs were equal, this method would take the left record first. This can preserve the original relative order of distinct records with equal keys; we are not combining records into one dictionary entry. This directory has no equal IDs.

Break the condition

What happens if left [18, 7] and right [4, 24] are merged by the same head-selection rule without sorting them first?

Compare my counterexample

Take 4, then 18, then 7, then 24: [4, 18, 7, 24]. It is not fully sorted. Merging does not automatically sort unsorted pieces; we first need a way to sort those pieces.

03 · Request the same task on a smaller input

“Sort half” is also
a smaller instance of the same problem.

Recursion means an operation calls itself on a smaller input. sort([18, 7, 24, 4]) requests two smaller results: sort([18, 7]) and sort([24, 4]). It merges them once they return. But we must also say when the smaller calls stop.

The base case and shrinking input

0 or 1 records are already sorted: return them unchanged; do not split or merge. With at least two records, halve the length and round down: the left gets the first ⌊n/2⌋ records and the right gets the rest. Both pieces are smaller than before; eventually we reach a base case.

sort(records):
    if there are 0 or 1 records, return records
    left = sort(first half)
    right = sort(second half)
    return merge(left, right)

This lesson follows the order complete the left call first, then the right call, then merge in the caller. A split diagram shows all subproblems; it does not mean they run at the same time.

sort([18, 7, 24, 4])
First [18, 7], then [24, 4]; merge once both results return.

sort([18, 7])
[18] and [7] return from base cases → [7, 18].

sort([24, 4])
[24] and [4] return from base cases → [4, 24].

The caller continues
[7, 18] and [4, 24] → [4, 7, 18, 24].

There are 7 calls: one with four records, two with two records, and four with one record. n is still 4; calls are not records. Returning from one base call does not finish the whole algorithm; the waiting caller continues from where it paused.

04 · Sort pieces with the same method

Split, wait for the results,
merge the sorted pieces.

This method is called merge sort. In the four-record example, the lower merges [18]+[7] and [24]+[4] use 2 comparisons and 4 placements in total. The final merge [7, 18]+[4, 24] uses another 3 comparisons and 4 placements. Whole sort: 5 comparisons, 8 placements.

Trace the small example first. Then select “8 records” to apply the same method to the whole directory. At each step, state which call is waiting for results and what is being merged now.

Predict the next decision first

Each example resets the initial state. “Merge” counts only one merge of ready-made sorted pieces; the other examples count the whole sort. ID comparisons and output placements are separate units.

All revealed steps

    Open calls are nested tasks; no concurrent execution is shown. The teaching trace stores every intermediate state; these display records are excluded from the algorithm’s memory requirement.

    Compare all directory merges on paper

    First half [18, 7, 24, 4]: [18]+[7] → [7, 18], 1/2; [24]+[4] → [4, 24], 1/2; [7, 18]+[4, 24] → [4, 7, 18, 24], 3/4. Total 5 comparisons / 8 placements.

    Second half [11, 20, 31, 26]: [11]+[20] → [11, 20], 1/2; [31]+[26] → [26, 31], 1/2; [11, 20]+[26, 31] → [11, 20, 26, 31], 2/4. Total 4 comparisons / 8 placements.

    Final merge: [4, 7, 18, 24]+[11, 20, 26, 31] → [4, 7, 11, 18, 20, 24, 26, 31], 6 comparisons / 8 placements. The whole sort uses 15/24; only the final merge uses 6/8. Eight one-record base calls and seven split calls make 15 calls in total.

    The counting units

    One comparison: comparing the two head IDs while both pieces still have records. One output placement: adding a whole record to that merge’s output array. Taking the remainder is also a placement, not a comparison.

    The placement counter does not count every physical memory write, subarray copy, control condition or screen rendering. A record can be placed again in different merges; this is why 8 records involve 24 placements. Counters are not seconds.

    05 · Count the layers, build the formula

    n records in each layer.
    How many merge layers?

    First consider n = 2ᵏ, a power-of-two size. Eight records shrink as 8→4→2→1: 3 halvings. On the way back, 1+1→2, 2+2→4, 4+4→8: 3 merge layers. k = log₂n: how many factors of 2 we multiply to reach n.

    Singles to pairs: 4 merges × 2 records = 8 placements.

    Pairs to fours: 2 merges × 4 records = 8 placements.

    Fours to eight: 1 merge × 8 records = 8 placements.

    The total merged size is n at each layer. In this model, for a power-of-two n, all merges therefore make output placements P(n) = n log₂n. For n=8, P(8)=8×3=24. This is not an exact formula for comparisons: our example has C=15. Which half runs out first changes the comparison count.

    If n doubles

    Compare sizes on paper

    n=1: 0 merge layers, 0 placements. n=2: 1 layer, 2 placements. n=4: 2 layers, 8 placements. n=8: 3 layers, 24 placements. n=16: 4 layers, 64 placements. When the data doubles, we double the old work and add the new top layer’s 2n placements: P(2n)=2P(n)+2n.

    If n is not a power of two, the halves may be unequal; for example, 5 first splits into 2 and 3. We do not claim that every layer makes exactly n placements or that n log₂n is an exact count. The number of halvings remains logarithmic, and total merging work in a layer is at most on the scale of n.

    Connect to compact notation

    This basic version uses no optimisation such as skipping a merge when the input is already sorted. Assuming constant work per record comparison and placement, total algorithm work is on the scale of Θ(n log n); n≤1 has constant base-case work. The exact comparison count depends on the input. Auxiliary output space can be kept linear and active recursion depth logarithmic; the total call count is not the number of simultaneously open calls. Storing every snapshot of the teaching trace takes additional space.

    This method allocates extra space for merging. If we need only a few highest-priority jobs, we do not have to sort the whole directory. Output and memory requirements also inform the method choice.
