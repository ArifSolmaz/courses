From connections to dependencies

In what order
can maintenance jobs finish?

We will maintain the devices at the pump, greenhouse, warehouse and gate. Some jobs must finish before others. Can we propose an order, or do the requirements make each other impossible? Using the same devices, let us now plan the dependencies between jobs.

01 · The goal has changed

Which job must finish first,
rather than the fewest connections?

In Week 8 connections carried messages in both directions; we used a FIFO queue to find the fewest edges. Now each vertex represents one maintenance job at the same device. An arrow carries a different meaning.

The arrow contract

A→B: job A must finish before B can start. For example, 18 → 7 requires the pump job to finish before the greenhouse job. It does not mean 7 → 18, nor does it represent a message connection.

The input is all jobs and their directed dependencies. The output is an order containing every job exactly once, placing the left-hand job first for every arrow, or a directed cycle showing that no such order exists. We are not calculating job durations, a parallel schedule or the shortest total completion time.

Is ID order enough?

Why does [4, 7, 11, 18, 20, 24, 26, 31] fail the 18 → 7 requirement? Is a smaller ID a priority rule?

Compare my decision

7 is written before 18, but the arrow requires 18 to finish first. Sorting records by ID does not resolve dependencies. The arrows constrain the permitted order.

03 · Save the return position

Explore the child.
Then return to the arrow where you left off.

The calls in Week 7 finished the smaller task and returned to the caller. Here DFS, depth-first search, descends to an unentered neighbour; when that call returns, it continues with the remaining neighbour. A LIFO stack returns the most recently entered call first.

Distinguish three states

Unentered: DFS has not opened this job yet. Active: its call is open and on the stack. Finished: all its outgoing arrows have been examined and its call has returned. These are states of the search call.

DFS computes the plan; it does not perform maintenance. Entering a vertex does not mean that the job has started, and returning from a call does not mean that actual maintenance has finished. The search trace and the job order to execute are separate.

  1. First call: 18. Read 18 → 7; enter 7. Stack from bottom to top: [18, 7].
  2. Read 7 → 4; enter 4. It has no outgoing arrows; finish and return. The stack is [18, 7] again; the next neighbour of 7 is 11.
  3. Enter 11, then 31. When 31 returns, 11 continues where it left off.

The stack holds only calls that are open right now. Finished 4 is no longer on the stack. Each frame stores an ID and the next neighbour position.

04 · Predict the next event first

Enter, inspect an arrow,
return.

To make the trace reproducible, we choose 18 first, then the remaining unentered jobs in increasing ID order as roots. Outgoing neighbours are also in increasing order. This is our example’s choice rule, not a condition for DFS correctness.

all jobs: unentered
for each root candidate u:
    if u is unentered, call DFS(u)
DFS(u):
    mark u active; put the call on the stack
    for each outgoing neighbour v of u:
        if v is unentered, call DFS(v); then return here
        if v is active, show the cycle and stop the whole search
        if v is finished, continue without calling it again
    mark u finished; append to the finish list; return
if no cycle was found, reverse the finish list

In the demonstration, inspecting an arrow and entering a new neighbour are two separate steps. Reading the arrow advances the caller’s position; the child enters the stack on the next step.

Trace the stack and returns

Changing the example resets the initial state. The whole search stops at the first cycle. To claim there is no cycle, we examine every job, not just the first root. This search does not carry out maintenance.

      05 · Demonstrate a contradiction

      Look for an arrow back to an active ancestor,
      rather than any previously seen vertex.

      When 24 → 11 was read, the call for 11 had finished; this is not evidence of a cycle. If we add 31 → 7 to the main network, the stack while examining 31 is [18, 7, 11, 31]. 7 is still active.

      A directed-cycle witness

      The call path is 7 → 11 → 31; the new arrow is 31 → 7. Together they form 7 → 11 → 31 → 7: a closed chain in which every step is a real arrow. 7 must finish before 11; 11 before 31; and 31 before 7. 18 can reach the cycle but is not part of this cycle.

      This strict “before” relation cannot lead back to the same job. No order satisfies all dependencies. Because we stop at the first cycle, active calls remain on the stack; we do not say that they returned. One witness is enough; we are not listing every cycle.

      If everything below 18 is clear, is the whole network clear?

      If we add only 26 → 26, no cycle appears in the calls from 18. Can we claim “no cycle”?

      Compare my claim

      No. 26 must be examined as a separate root. It sees itself active; [26, 26] is a one-arrow cycle witness. The outer loop covers every job. In the main example, we must include 26 in the order even though it has no arrows.

      06 · From search trace to job plan

      If there is no cycle,
      reverse the finishes.

      A directed acyclic graph is called a DAG. When the whole search finishes without a cycle, the finish list is [4, 31, 11, 7, 20, 24, 18, 26]. Its reverse gives a topological order:

      [26, 18, 24, 20, 7, 11, 31, 4]

      For every arrow u→v, u must come before v. For example, 18 → 7: 18 is in the second position and 7 in the fifth; 24 → 11: 24 is third and 11 sixth. Check all eight arrows.

      Why do reverse finishes work?

      When u→v is read, if v is unentered, its call finishes before u returns. If v is finished, it has already finished before u. If v is active, there is a cycle; that case cannot occur in a DAG. Therefore v finishes first, then u. Reversing the list puts u before v.

      This is not the only valid order. [18, 7, 24, 4, 11, 20, 31, 26] also satisfies every arrow. Independent 26 may occupy different positions. We do not impose ID order on jobs with no required relationship.

      In a cyclic graph, reversing a partial finish list does not produce a solution. DFS entry order is not a general rule for a topological order either. We also check that the candidate contains every job once and makes every arrow point forward.

      07 · Keep the unit explicit

      8 jobs, 8 directed arrows.
      How much work does the search do?

      In the main DAG, V=8 state rows are initialised; 8 calls are entered and 8 calls return. Every outgoing list is scanned once: E=8 adjacency entries. The maximum stack length is 4; the total number of calls is 8. “Length” here counts frames; the edge depth of the 4-vertex call path is 3.

      What assumptions support O(V+E)?

      With ready-made lists, initialise/enter/finish each job once and inspect each directed entry once: O(V+E) work. Reversing the finish list takes O(V); checking a candidate order against all arrows takes O(V+E). Constant-work state access and pushing/popping at the top of the stack are assumed.

      States, parents, finishes and at most V active calls require O(V) auxiliary space; the graph representation takes O(V+E). Building/sorting lists and storing every teaching snapshot are excluded. The counters do not measure elapsed time or every memory write.

      In the 31 → 7 example, we stop early: 8 initialisations, 5 entries, 5 arrow scans and only 1 return. The remaining calls are active; do not treat this as an exact count for a full search. Worst-case work is still bounded by O(V+E); writing one cycle witness takes at most O(V) additional work.

      08 · Reduce the support

      7 has returned.
      Where does 18 continue?

      Suppose the call for 7 has just finished in the main DAG. The active stack is [18], the finish list [4, 31, 11, 7]. The outgoing list of 18 is [7, 24]; the first neighbour’s call has finished.

      Compare the solution after trying

      The second neighbour of 18 is 24. After entering, the stack is [18, 24], with length 2. 24 → 11 is examined; 11 is finished and off the stack. Continue to the next neighbour, 20, without calling the finished job again. The call for 18 waits until 24 returns. These calls compute the plan; we have not performed the actual maintenance for 11 early.

      I have finished · compare the answer and criteria

      Example answer

      1. Enter 18, 7, 26, 4; return from 4, 26 and 7. At 18, enter 24; do not call 26 again because it has finished. Return from 24 and 18. Then enter and return from the separate root 20. Finishes [4, 26, 7, 24, 18, 20].
      2. Reverse finishes [20, 18, 24, 7, 26, 4] give one valid order. [18, 7, 24, 26, 4, 20] is also valid: every job once, each predecessor first for every arrow. Do not forget independent 20.
      3. V=6, E=5; 5 directed-entry scans, 6 entries and 6 returns. The longest active stack is [18, 7, 26, 4], with length 4. The six calls are not all active at once. Because each v finishes before u, u→v points forward in reverse finish order.
      4. Adding 4 → 7 creates the 7 → 26 → 4 → 7 cycle; no valid order exists. An arrow to finished 26, namely 24 → 26, is not by itself evidence of a cycle.
      5. DFS computes the plan. LIFO finishes the child and returns to its caller; that call continues with its next neighbour. A directed arrow appears once in the lists. Covering all roots avoids missing a cycle in a separate component and includes every job in the order.
