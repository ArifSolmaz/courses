01 · From a given position to an ID

Without its position,
how do we reach it?

In Week 4, we said “read the record at k = 4”. Now the request is “retrieve the record information for ID 32”. 32 is not a position in a sequence; it is the key we are looking for.

We keep one current location label for each device. For example, 32 → “gate”. The answer is the information “gate”, rather than a position in a sorted directory. If the ID is not registered, the answer is “not found”.

State the contract first

If 32's label changes to “workshop”, do we need a second record for 32, or a new value for the same record?

Compare my reasoning

This task keeps one current record per ID: we replace the value for the same key. In Week 1, we could keep several arrival messages with the same ID; the purpose was different. Here, we are not storing the entire message history.

02 · Define the shared task

One dictionary.
Two basic operations.

The same contract for both representations

Key
A device ID. A dictionary has only one record for each ID.
Value
The device's location label, such as “pump”. Different IDs may have the same label.
get(id)
Return the record's information if it exists; otherwise return “not found”.
set(id, value)
Insert a new ID, or update its information if it already exists. An update does not increase the number of records.

n = 7 distinct keys. “Dictionary” defines the operations we need; a tree or a hash table can implement them. We will examine how the choice of structure changes the search path.

03 · Compare to choose a branch

Smaller keys go left.
Larger keys go right.

In a binary search tree, all keys in a node's left subtree are smaller than its key, and all keys in its right subtree are larger. When we encounter the same key, we replace its value rather than create a new node. The given insertion order creates these relationships:

Root 18

Left → 7
Right → 24

Node 7

Left → 4
Right → 11

Node 24

Left → 20
Right → 32

4, 11, 20 and 32 are leaves: they have no children. For get(32):

  1. 18 < 32 → go right, to 24. The left subtree cannot contain 32.
  2. 24 < 32 → go right, to 32.
  3. 32 = 32 → return “gate” and stop.

Three node comparisons. Here, one comparison is a single abstract operation that tells us whether the current key is smaller than, equal to or larger than the target. It does not count individual programming operators. When we reach an empty link, we return “not found”; there is no key there to compare.

Do the same seven keys always take three steps?

If we simply insert 4, 7, 11, 18, 20, 24, 32 in that order, every new key goes right. How many nodes do we visit to find 32?

Compare my trace

4 → 7 → 11 → 18 → 20 → 24 → 32: seven comparisons. Both trees hold the same dictionary. This simple insertion method does not balance the tree automatically.

Height bounds the path

h is the number of edges from the root to the deepest node. In the first tree, h = 2; the longest successful search takes h + 1 = 3 node comparisons. In the chain, h = 6 and the bound is 7. A single node has height 0; an empty tree requires no key comparisons.

In a tree that is kept balanced, height can grow logarithmically. The ordinary insertion method used here does not guarantee this: in the worst shape, it can produce a chain of n nodes. Having a tree alone does not guarantee a short search.

04 · Compute the bucket first

Same bucket.
Same ID?

Allocate m = 5 buckets in a hash table. The bucket label is ID mod 5: the remainder when the ID is divided by 5. The labels are 0, 1, 2, 3, 4; these are not the one-based positions used in earlier weeks.

32 mod 5 = 2 and 7 mod 5 = 2. Different keys land in the same bucket: a collision. Our solution here is chaining: keep records in the same bucket in a list, in insertion order. Append a new key at the end; if the same key is found, update its value in place.

0 → 20: garden

1 → 11: well

2 → 7: greenhouse → 32: gate

3 → 18: pump

4 → 24: warehouse → 4: roof

get(32): one hash computation; then 7 ≠ 32 and 32 = 32: two key equality checks, returning “gate”. get(16) goes to bucket 1; its only key, 11, differs, so one equality check returns “not found”. Finding the bucket does not mean we have found the right record.

Predict the decision, then reveal it

Selecting an example or representation rebuilds the starting state. The counters track only the selected get/set operation; they exclude the work of building the initial structure.

    Compare the traces and updates on paper

    Find 32: in the first tree, 18 → 24 → 32 takes three comparisons; in the hash table, computing bucket 2 and checking 7 → 32 takes two equality checks. Both return “gate”. Hash computations and equality checks have separate counters; they cannot be compared with tree comparisons as if these were seconds.

    Set 26: after comparing 18 → 24 → 32 in the tree, insert the new record to the left of 32. In the hash table, compute bucket 1 and make one equality check, then append 26 to the bucket's list. This is one logical set operation. Then finding 26 takes four tree comparisons, or one hash computation and two equality checks.

    Update 32: find the same key and replace its information with “workshop”. n is still 7; the tree's shape and the key order in the bucket are unchanged. Get in an empty dictionary: the tree makes 0 comparisons; the hash table makes one hash computation and 0 equality checks, returning “not found”.

    Separate load, average and worst case

    α = n/m is the average number of records per bucket. Here, 7/5 = 1.4. This does not mean that every bucket holds 1.4 records, or that the worst search takes 1.4 checks.

    If keys are distributed sufficiently evenly among buckets and a hash computation is treated as constant work, the expected search work is expressed on the scale of 1 + α. If α is kept bounded, the expected work can remain constant in scale. With fixed m, α grows as n grows. If all keys land in one bucket, searching that bucket may require checking up to n keys.

    Connect this to compact notation

    Under these assumptions, chained hashing has expected O(1 + α) work, or expected O(1) when the load is bounded. The worst bucket scan is O(n). The expectation depends on a distribution assumption; this mod 5 example does not guarantee good distribution. These notations summarise a scale of growth; they do not measure seconds.
