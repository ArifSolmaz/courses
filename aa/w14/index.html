01 · A new rule for the same answer

Four edges, cost 10.
Still valid?

In Week 13 we found the walk 24 → 20 → 32 → 20 → 32: exactly four edges, cost 4+2+2+2=10. Repeated devices were allowed. Now change just one condition: each device may be used at most once. The same candidate repeats 20 and 32; it is invalid under this new contract.

The source, target, network, and edge costs stay the same. The candidate with no repeated devices is 24 → 18 → 7 → 11 → 32: four edges and 3+2+2+5=12. Checking this list does not require generating every alternative. But “Is 12 the minimum?” is a separate claim; seeing that a list is valid does not prove it.

Why can we not use last week’s table unchanged?

D[v, r] stored only the device and the number of edges used. With repeated devices forbidden, the devices already used in a prefix affect which continuations are allowed. Two prefixes ending at the same v,r may allow different continuations; keeping only the cheaper prefix is not generally sufficient.

This observation does not prove that “DP is now useless” or that “a fast method for this problem is impossible.” It shows that the previous state definition is insufficient for the new condition.

03 · Choose the type of output

Instead of “What is the minimum cost?”
ask “Does any fit the budget?”

A decision problem asks for a YES or NO answer for every input. Call this lesson’s main problem family L:

L · A simple path with exactly k edges within a budget

Input: a simple undirected graph G, nonnegative integer edge costs, a source s, a target t, an edge count k, and a budget B. 0≤k≤V−1; V is the number of devices. All devices are listed in the input.

Question: Is there a path starting at s and ending at t, using exactly k edges, no repeated devices, and total cost at most B? If such a path exists, answer YES; if no candidate meets the conditions, answer NO. We are not asking for at most k edges or the minimum cost.

The main example has s=24, t=32, k=4. The candidate with no repeated devices and cost 12 is a YES witness for B=12; it exceeds the budget for B=10. Rejecting it at B=10 does not by itself rule out every other candidate.

I saw a bad list: is the answer NO?

Your friend’s candidate contains a missing edge. What can you conclude?

Compare my claim

Only this candidate is invalid. Another candidate may meet the question’s conditions. Answering NO requires a separate correct method or justification showing that no valid candidate exists. Our checker does not search for candidates.

04 · Give a witness for a YES answer

A certificate is a path list.
The checker does not find it.

A certificate is extra information supplied to support a YES answer. For L, a list of k+1 devices is sufficient: [24, 18, 7, 11, 32]. The person supplying the list may have found it; the checker’s task is to check whether the given list meets every condition.

  1. Does the list contain exactly k+1 entries? Is every ID in the graph?
  2. Is the first device s and the last t? If repetition is forbidden, are the IDs distinct?
  3. Is each consecutive pair a real edge? Add the edge costs.
  4. Is the total ≤ B? If every check passes, this candidate is accepted and provides a YES witness for the decision question.

If a check fails, this certificate is rejected. “Candidate accepted” differs from “minimum proved”; “candidate rejected” differs from “the answer to the question is NO.” A short certificate check does not mean we have given a method that always finds a correct certificate quickly.

Because k≤V−1, the certificate contains at most V IDs. Encoding devices by their indices in the input list takes O(V log V) bits; for V=1, use one constant-size entry. Certificate length is bounded by a polynomial in the input size.

05 · Make the checks visible

Check one condition.
Keep the conclusion precise.

check(G, s, t, k, B, candidate):
  if length is not k+1, reject the candidate
  if any ID is not in the graph, reject the candidate
  if first ID is not s / last ID is not t, reject the candidate
  if repeats are forbidden and an ID repeats, reject the candidate
  total = 0
  for each consecutive pair u,v:
    if the edge does not exist, reject the candidate
    total = total + w(u,v)
  if total > B, reject the candidate
  accept the candidate

The demonstration stops at the first failed check. Checking that an edge exists and adding its cost to the total are separate steps. The display shows only the cost of the prefix actually checked; it does not invent a complete candidate cost when an edge is missing.

    06 · The work of checking and searching

    Scan one list.
    Do not scan every list.

    Given a prepared edge dictionary and ID set, if each membership or edge lookup is counted as a constant-cost abstract operation, checking one k-edge candidate takes O(k+1) checks and O(k+1) space for the repeat set. It may finish earlier at the first error. Preparing the dictionaries and reading the input graph require additional work; the model’s counters exclude it.

    The polynomial claim does not depend on one data structure’s expected access time: even without dictionaries, scanning the input lists for each ID and edge gives a polynomial upper bound such as O((k+1)V+kE) comparisons. Reading weights/B, adding costs, and comparing them also take work polynomial in the number of bits used to write the numbers. The display’s “4 additions” does not guarantee four machine instructions.

    Which input size?

    The classes describe a problem family with varying devices, links, s,t,k,B, and weights, rather than this one eight-device example. In L, k≤V−1 and the certificate has at most V entries. Counting k by its numerical value differs from counting the length of its binary encoding.

    Week 13’s O(k(V+E)) bound was proportional to k; for binary-encoded, arbitrarily large k, we do not directly declare it polynomial in the bit-input size. For the simple-path family here, k≤V−1 prevents this length issue. The demonstration’s limit of 32 devices/k≤32 is only a teaching limit.

    The demonstration stores copies of every event and state. Trace history, screen rendering, validation, and dictionary preparation are excluded from the “ID/edge/addition” counters. Distinguish the basic checker’s space from the space for the entire teaching record.

    07 · From one example to a problem family

    P and NP
    are not “easy and hard” boxes.

    P · Solve the decision question

    Decision problems with a deterministic algorithm that gives every input’s YES/NO answer in time bounded by a fixed polynomial in the input length.

    NP · Verify YES

    A verifier checks certificates of polynomial size in the input length in deterministic polynomial time: for YES inputs it accepts at least one certificate; for NO inputs it accepts none.

    P⊆NP. If you can solve the question in polynomial time, you can also verify YES without needing a certificate. NP does not stand for “non-polynomial”; it comes from nondeterministic polynomial time. Whether P=NP or P≠NP remains unknown. Membership in NP does not prove non-membership in P.

    For L, the list is short and checking is polynomial: L∈NP. This does not say that our checker finds a short document for every NO input. “Every candidate I tried failed” is not a NO certificate unless all candidates have been proved exhausted.

    A problem is NP-hard if every problem in NP reduces to it in polynomial time. If it is both in NP and NP-hard, it is NP-complete. This label does not prove that every small instance is hard, an exponential lower bound, or P≠NP. A general polynomial algorithm for any single NP-complete problem would imply P=NP. A polynomial bound also does not guarantee practical speed at every input size.

    Make a claim about a class

    “I checked a path list quickly, so I can find every valid path quickly.” Has this implication been proved?

    Compare my inference

    No. Verification gives the two parts needed for NP membership: a short certificate and a polynomial check. A general polynomial decision algorithm has not also been shown. This lesson has not resolved the P/NP equality question.

    08 · The arrow tells you how to use a solver

    Convert A to B.
    Solve A with a B solver.

    A≤ₚB means: convert every A input in polynomial time into a B input called f(x), with x∈A ⇔ f(x)∈B. YES and NO are both preserved. We can then use the answer from an assumed solver for B as the answer for A.

    1. A input xThe question I want to solve
    2. Polynomial transformation fConvert the input to B’s contract
    3. B solverAsk the assumed solver about f(x)
    4. The answer for AThe same YES/NO by equivalence

    Therefore, if A≤ₚB and B∈P, then A∈P. This supports B being at least as hard as A. To show that B is hard, start from a known hard A and go in the A → B direction. The reverse arrow does not establish this claim.

    One concrete reduction · UHAMPATH → L

    A: in a given undirected graph G, is there a Hamiltonian path from the given s to t visiting all V devices exactly once? The NP-completeness of this problem family with specified endpoints is our known starting theorem; we do not include its lengthy proof in this lesson.

    f: keep the graph, s, and t. Set every edge cost to 1; choose k=V−1, B=V−1. L’s contract already forbids repetition. Here we deliberately change the weights; we are not pretending to solve the original cost question from the first part.

    Forward: A Hamiltonian s→t path contains V distinct devices; with V−1 edges of unit cost, its total is V−1. It is a valid certificate for L.

    Reverse: An L certificate uses V−1 edges with no repeated devices, so it has V distinct device positions. It covers every device in the graph exactly once and is a Hamiltonian s→t path. This establishes both directions and preservation of NO answers too.

    Copying the V/E lists, writing 1 for each edge, and encoding V−1 take polynomial time in the input length. Together, A being NP-complete, A≤ₚL, and L∈NP establish NP-completeness of this general L family. One eight-device example cannot replace this proof.

    Apply the transformation by hand to a small device chain

    V=[4, 7, 18, 24], with only 18 – 24, 24 – 7, 7 – 4; s=18, t=4. A witness for A is 18 → 24 → 7 → 4. The transformation sets these same three edge costs to 1, with k=3 and B=3. The same list is accepted for L; total 3. We did not carry the original costs 3, 1, 2 into this unit-weight demonstration.

    If the graph were a star centered at 24 with leaves 18/7/4, there would be no Hamiltonian s=18, t=4 path: after visiting leaf 7, reaching t would require returning to 24. The transformed L instance also has no simple path with V−1 edges. These two small examples illustrate the general proof in both directions; they do not replace it.

    After completing your work, open the model answer and criteria

    Example answer

    1. Both candidates contain four known, distinct IDs, have endpoints 18/4, and use three edges. Y’s running total is 0 → 3 → 4 → 6; 6≤6, accept. Z’s running total is 0 → 1 → 2 → 9; 9>6, reject for exceeding the budget. Despite Z’s failure, Y makes the decision answer YES.
    2. 6, 9, 3, 3. The transformation has k=V−1=3 and B=3; every edge costs 1. Four positions with no repeated devices cover all V devices. Do not confuse this transformation’s budget with the original B=6.
    3. Accepting Y gives a YES certificate; it proves neither minimum cost nor fast solution of all inputs. The certificate has at most V entries; encoding by index uses O(V log V) bits. Membership, endpoint, repeat, edge, and bit-arithmetic checks are polynomial. NP requires a short, correct certificate check for YES; it does not require a short witness for NO. P⊆NP and the equality question remains open.
    4. UHAMPATH → L. Convert the A input to L with unit weights/k=B=V−1; ask the L solver and use the same answer. UHAMPATH’s known NP-completeness gives NP-hardness; also showing NP membership through L’s short certificate and polynomial check gives NP-completeness.
    5. The previous DP kept only the cheaper prefix at the same v,r. Forbidding repeats changes which devices from the prefix remain available later; forgetting this history is not generally safe. An insufficient state definition is not an impossibility proof for all algorithms.

    Four separate criteria

    0=I could not produce it / there is a basic contradiction; 1=partly correct or I received a hint; 2=I produced a consistent, justified answer without seeing the solution. Mark corrections after seeing the solution separately from the first independent attempt.

    • Mathematics: did you explain k+1, ≤B, certificate size, and both directions of the transformation?
    • Purpose: did you distinguish accepting/rejecting a candidate, the decision answer, and minimum-cost claims?
    • Connections: did you justify the limits of the DP state and using the solver in the A→L direction?
